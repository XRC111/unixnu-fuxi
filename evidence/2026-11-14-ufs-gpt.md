# 2026-11-14 UFS survey: NativeUfs reads the LUN 0 GPT on fuxi

Owner: XRC111. Device: Xiaomi 13 (fuxi, SM8550, 2211133C, China), 8 GiB RAM + 256 GB, slot a,
bootloader unlocked, HyperOS 4.0.0.12.XMCCNXM.

Image: run 43555808433 of the Build workflow, built from `c02e432` (device repository) which
carries the ShengUfs component, `native-ufs-probe=9` and the empty-policy VerifiedRoot stub.
boot.img sha256 `d4b145c54edeaf03be62d512042adc5b6ee53ee2ec47fd28c3437e5455cf3ab14` (144,723,968
bytes), prelinked kernel sha256 `37abada06301e2e23735004e588474a416c148ee66260ea973626dd5515cdc91`.

Method: `fastboot boot` only; nothing was written to the device. The probe adopts the controller
the firmware left running, wakes the device with START STOP UNIT (power condition ACTIVE) and
issues read-only SCSI commands (TEST UNIT READY, READ CAPACITY, INQUIRY, READ(10)).

(Some LBA columns wrap on the panel; the two entries that matter here, `super` and `userdata`, are
unambiguous, and the GPT header's own fields — first/last usable, backup LBA — agree with them.)

What this proves on fuxi:

- The controller was adopted from the firmware's state without a reset, the request list was
  replaced, and commands completed (the header and entry CRCs the probe prints are the values the
  device returned, `EFI PART` was accepted by the probe's own validation).
- The apps-SMMU stream the driver selects reaches the controller: without a working stream the
  READ(10) calls would have faulted or returned nothing.
- LUN 0 reports a 4096-byte block size and a GPT with 32 entries, which is the stock Xiaomi layout.

## Partition geometry (LBA in 4096-byte blocks)

| Entry | Range | Blocks | Size |
| --- | --- | --- | --- |
| `super` | `0xb7840` .. `0x2f783f` | 2,490,368 | 9.5 GiB |
| `userdata` | `0x2f7840` .. `0x3afc3fa` | 58,739,643 | 224.1 GiB |

`userdata` first/last are **exactly** the values kkkpc's port adopted from mouse233 for the
"same specification" 12+256 unit (`first_lba 0x2F7840`, `last_lba 0x3AFC3FA`). This unit is 8+256
and the layout is identical, so the LBA constants other fuxi ports recorded for the 12 GB model
apply unchanged to the 8 GB model. That is a useful cross-check: the earlier assumption that the
two RAM variants might differ in GPT didn't hold.

## What this opens

A 32 GiB UniXNU partition carved from the end of `userdata` (the aston layout) would sit at:

- `unixnu`  `0x32fc3fb` .. `0x3afc3fa`  (8,388,608 blocks = 32.0 GiB)
- `userdata` shrunk to `0x2f7840` .. `0x32fc3fa`  (50,351,035 blocks = 192.1 GiB)

Doing that means rewriting the primary and backup GPT and shrinking the Android filesystem, which
is a write operation and has not been attempted. Everything above is read-only evidence.

## Notes

- The probe also confirms the empty-policy VerifiedRoot stub is enough to link and run the driver
  with `NATIVE_VERIFIED_BLOCK=1`: the run reached `adoptAndRead` and the GPT survey, and
  `configureVerification` is never reached in probe mode.
- `CONFIG_XNU_NATIVE_UFS=y` alone would not have done anything: `NativeUfs::start()` returns false
  unless `native-ufs-probe` or `native-ufs-root` is set (the same finding Kerfand records).
- No UFS read of a user partition's contents was attempted; only GPT metadata was read.
